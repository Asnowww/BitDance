## 接口与数据契约

### 主要 API

由 Architect Agent 在每个功能点开发前补全，记录在该区块。当前已约定：

- `POST /auth/sms/send`：手机号短信验证码发送，请求体 `{ phone }`，响应 `{ sent, expiresIn }`。
- `POST /auth/login`：手机号 + 验证码登录，请求体 `{ phone, code }`，响应 `{ token, user }`，其中 `user = { id, phone, nickname, avatar, roles }`。
- `GET /studios/nearby`：附近舞室列表，参数 `latitude / longitude / city / page / pageSize / sort`，响应 `{ list, page, pageSize, total }`，列表项含 `id / name / cover / city / area / distanceKm / ratingAvg / reviewCount / topStyles / beginnerFriendly`。
- `GET /studios/{id}`：舞室详情，附 `intro / address / openHours / photos / courses`。

### 数据库表结构

以 `bitdance_postgresql_schema.sql` 为准。

### 模块间通信

前后端通过 RESTful + Bearer token，统一返回 `{ code, message, data, traceId }`，前端拦截 `code === 0 / 200 / 'SUCCESS'` 视为成功。

- 改动范围：community 包 7 实体（其中 ContentLike / ContentPostTopic / FollowRelation 走 @IdClass）+ 7 Repository + 1 CommunityService（14 个方法、单文件聚合所有子域避免跨 service 调用）+ 1 CommunityController（15 个端点）+ CommunityControllerTest 26 例。
- 关键问题与解决：① feed 列表 N+1：原本每个 post 单独查 likeCount/commentCount/topics 会 3N 次往返，改用 `countGroupedByPostIds`（GROUP BY postId）一次拉全部计数 + `findLikedPostIds(userId, ids)` 一次拉当前用户已赞集合 + `findByPostIds` 一次拉 post→topic 映射，feed 列表查询从 1+3N 降到 4 次。② content_like 复合主键无独立 id：用 `IdClass(ContentLike.PK)`，toggle 走 `existsById(pk) → deleteById(pk) | save(...)` 三段路径；follow_relation 同理。③ 用户输入的话题在 topic_tag 表里可能不存在：findByTopicName 找不到时自动建表（topic_code 用时间戳+hash 占位防 uk 冲突），creator_user_id=当前用户、is_system=false；schema topic_tag 有 topic_name uk 所以并发可能 race，本期单机不处理，BE-015 加 Redis 锁。④ visibility=followers 的可见性校验在 detail() 里走 follow_relation.existsByFollower+Followee；feed scope=follow 取我关注的 ids 再 JPQL 过滤。
- 方案选择理由：单 service 而非拆 PostService / CommentService / FollowService 三个，是因为 enrichBatch（feed 项填充 likeCount/commentCount/topics/liked）必须复用，跨 service 互相注入会造成循环或重复代码；MVP 阶段 14 个方法在一个 service 还能管理。`content_post` 没有 like_count/comment_count/share_count 反向计数列（schema 故意不冗余），所以走 GROUP BY 实时聚合而非每次写都 UPDATE+1；并发安全且代码简单，热门帖性能问题留 BE-015 加 Redis 缓存解决。举报防重复用 `existsByReporter+Target+StatusIn(pending,processing)` 而不是 uk 约束，schema 没建复合 uk，且业务上允许同一个用户对同一对象多次举报（举报 closed 后再次出现问题可以再报）。

### 2026-05-11 ｜ 第五组 ｜ BE-008 M2 Review 评价 + 雷达图 + 风控权重

- 目标与背景：W3 起步。M2 是 MVP 决策闭环的关键一环——结构化评价，包含维度评分、加权聚合、风控权重三大子系统。schema 在 review/review_dimension_score/review_reply/review_appeal 上做了细致约束（overall_score 1-5、维度 score 1-5、status 五值、weight_factor numeric(6,3)、risk_level smallint）。本轮交付用户侧全栈，回复与申诉留到 BE-014。

### 2026-05-09：用户端与教练端统一为 Vue H5 移动端，不再开发微信小程序

- 决策内容：用户端与教练端共用同一份 Vue 3 + Vite + TS + Vant H5 工程，先以浏览器 H5 上线，阶段 B 收尾后使用 Capacitor 打包为 Android APK 分发。

- 影响范围：架构文档（已修订）、API 路径（新增 `/api/h5/**`，保留 `/api/mp/**` 双写过渡）、登录方式（MVP 阶段以手机号验证码为主，微信登录降级为可选项）、消息通知（订阅消息降级为站内信 + 浏览器通知 + 后续 APK 推送）。
