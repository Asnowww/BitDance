## 适用范围与判定口径

- 本文只覆盖用户侧的 M1、M2，不展开商家侧、平台侧的详细操作步骤。
- 本文用于后续实现拆解、联调和验收，不用于替代《产品立项说明书》第 4 章本身。
- 需求真源为 `build/backend/【第五组】【组长：顾远】【BitDance舞室点评项目产品立项说明书】.pdf` 第 4 章。
- 现实入口真源为 `build/frontend/src/router/index.ts`、相关页面组件、现有公开/登录后接口。
- 现实交互与完成度真源为 `build/docs/BD-F-第4章产品方案与功能设计完成度核验总结.md`。
- 若页面文案、按钮样式、交互动作之间存在冲突，以用户对文字和视觉的自然理解为判定标准，而不是以当前实现自洽为标准。

### 控件审计硬规则

1. 正交性：一个控件只承载一个原子意图；不同控件不能用不同文案做同一件事，除非主次关系明确。
2. 语义一致性：控件文字、视觉样式、点击后结果，必须符合普通用户对该控件的自然理解。
3. 禁止隐式默认动作：未明确选中对象时，不能默认把动作施加到第一条数据。
4. 禁止伪输入控件：看起来像搜索框/筛选项的控件，如果不能直接编辑或直接改变条件，就不能伪装成输入控件。
5. 禁止状态与动作混写：用于展示当前筛选状态的标签，不应同时伪装成另一类动作入口。

## 5. 搜索结果页问题详解

`http://localhost:5173/#/search` 当前是 M1 的核心承接页，但它同时承担了“看附近结果、筛选、地图浏览、选择对比对象、快捷收藏”五类任务，已经出现明显的语义和正交性问题。后续实现应优先按下面口径收敛。

### 5.1 伪搜索框

- 当前形态：顶部控件视觉上是搜索框，展示固定文案。
- 当前行为：点击后不是进入搜索编辑，而是直接返回上一页。
- 用户自然理解：这里应该能改关键词、改城市、重新搜索，至少也应进入明确的搜索输入态。
- 结论：这是典型的“伪输入控件”，必须整改。
- 直接决策：
  - 方案 A：改成真正的“搜索入口/修改关键词”控件。
  - 方案 B：保留不可编辑，但改成非输入样式的“当前结果摘要条”，例如“北京 · 附近舞室结果”。

### 5.2 筛选入口混杂

- 当前形态：`舞种 / 距离 / 价格 / 时段 / 舞室` 看起来像五个单独筛选器。
- 当前行为：点击任何一个都统一打开同一个总抽屉。
- 用户自然理解：点击“距离”应该直接改距离，点击“价格”应该直接改价格，至少也应打开对应维度的局部选择面板。
- 结论：这是“状态展示”和“总筛选入口”的混写。
- 直接决策：
  - 方案 A：保留 chip，但每个 chip 只控制一个维度。
  - 方案 B：chip 改成当前筛选状态展示，另设单独“筛选”按钮打开总抽屉。

### 5.3 `activeFilter` 高亮误导

- 当前形态：chip 会出现高亮态。
- 当前行为：高亮表达的是“最近点击的是谁”，不是“当前已生效的是谁”。
- 用户自然理解：高亮通常意味着“这个条件正在生效”。
- 结论：这是状态反馈语义错误。
- 直接决策：
  - 高亮必须与真实已应用的筛选条件绑定。
  - 如果仅仅是最近操作痕迹，就不应使用筛选生效态样式。

### 5.4 隐式收藏第一项

- 当前形态：页面底部有“收藏”动作。
- 当前行为：如果用户没有显式勾选对象，就默认对第一条结果执行收藏。
- 用户自然理解：收藏动作应只作用于“我当前明确选中的对象”。
- 结论：这是禁止出现的隐式默认动作。
- 直接决策：
  - 无明确选择时禁用“收藏”或提示先选择。
  - 不允许默认把动作落到第一条结果。

### 5.5 “查看详情”与整卡点击重复

- 当前形态：结果卡片本身可点击进入详情，卡片内部又用文案表达“查看详情”。
- 当前行为：两个入口本质上做同一件事。
- 用户自然理解：如果有两个不同表现的入口，通常期待它们作用不同。
- 结论：这是重复动作语义，会增加界面噪音。
- 直接决策：
  - 若保留整卡点击，则去掉“查看详情”伪按钮文案。
  - 若保留“查看详情”按钮，则整卡不应再作为同级主动作。

### 5.6 多主任务同屏竞争

- 当前形态：地图/列表切换、筛选状态、对比勾选、快捷收藏都在同一层级抢注意力。
- 用户自然理解：搜索结果页的主任务应该先是“看有什么”，其次才是“缩小范围”或“加入对比”。
- 结论：当前页面的任务层次感不够，容易让用户误以为自己需要同时完成多件事。
- 直接决策：
  - 第一优先级：结果浏览。
  - 第二优先级：筛选。
  - 第三优先级：对比与批量动作。
  - 页面布局和按钮强度都应按这个优先级重排。

## 6. 需要优先整改的语义/正交性问题清单

### P0：会直接导致误操作或错误理解

1. `/search` 顶部伪搜索框：看起来能搜索，实际返回上一页。
2. `/search` 底部收藏默认作用到第一条结果：属于隐式默认动作。
3. `/me/trials` 状态 chip 只高亮不筛选：会让用户误以为已经在看特定状态记录。

### P1：会持续增加认知负担，削弱 M1 主链路清晰度

1. `/search` 筛选 chip 与总筛选抽屉语义混杂。
2. `/search` `activeFilter` 高亮错误表达“最近点击”而不是“当前生效”。
3. `/search` 整卡点击与“查看详情”重复。
4. `/search` 地图/列表、筛选、对比、收藏同屏竞争，主任务不突出。

### P2：会造成页面任务语义偏移，但不一定立刻阻塞流程

1. `/favorites` 页头“学习数据”与页面主体“收藏管理”不一致。
2. `/coach/:id` 的“预约课程”实际先跳课程详情，动作名与结果不完全一致。
3. `/home` 部分快捷入口统一跳搜索页，文案需要更明确表达“带条件进入搜索”。

## 结论

从负责边界看，M1 的核心不是“把舞室信息摆出来”，而是把“发现 -> 筛选 -> 详情 -> 收藏/对比/试听预约”的决策链路做清楚；M2 的核心也不是“有写评价页就算完成”，而是让用户能理解自己评价的对象、状态和可信度结果。

从当前前端实现看，M1/M2 的页面数量和路由覆盖已经具备骨架，但交互语义还没有完全跟上，尤其是 `/search` 和 `/me/trials` 这种链路承接页，已经出现“用户按文字理解的事情”和“页面实际做的事情”不一致的问题。后续实现时，应优先按本文的语义规则收敛，再继续补功能细节，否则功能点越多，用户感受到的混乱会越明显。
