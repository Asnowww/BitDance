# AI实训助教平台产品立项建议书

## 一、项目概述

### 1.1 项目名称

TrainMentor AI 实训助教平台

### 1.2 项目定位

面向高校软件工程、计算机类专业实训教学场景的 AI
原生教学辅助平台。系统以教师端和学生端为基础形态，平台以"AI
智能体陪伴实训全过程"为核心主张，覆盖从开题答辩模拟、过程代码审查、实时问题解答到成员贡献量化评分的完整教学闭环，直接解决当前实训教学中"师生有效交流时间极短、评价标准主观粗放、反馈链路严重滞后"三大结构性痛点。

### 1.3 立项结论

现有工具主要服务并未真正解决高校软件工程实训中的核心矛盾：教师时间稀缺、项目过程难评估、学生反馈不及时、组内贡献难量化、AI
使用容易滑向代写依赖。该项目具备明确场景、可实现的最小闭环和可验证的商业化路径，属于工程项目，不是科研概念项目。

## 二、为什么小组应当投入资源做这个项目

### 2.1 真实需求已经存在，而且在持续放大

软件工程实训不是单次作业，而是一个跨数周甚至跨学期的工程过程。当前多数高校仍采用“教师线下布置任务
-\> 学生提交文档或代码 -\> 教师集中检查 -\>
线下反馈”的方式。这个流程在班级规模扩大、学生项目差异增大、GitHub
协作普及后，已经暴露出明显问题：

1.  开题答辩时间极短，老师来不及系统性质疑学生方案，学生也来不及充分修正。
2.  教师无法快速判断项目真实进度，往往只能看演示结果或提交次数，难以发现过程性问题。
3.  GitHub 链接虽然提供了仓库入口，但老师没有时间逐个审查
    commit、PR、文档和需求偏差。
4.  每周指导时长有限，沟通往往没有沉淀，问题重复出现。
5.  组内评分高度依赖主观印象，缺少兼顾工作量与质量的客观建议。

| **痛点维度** | **具体表现** | **可量化的损失** |
|----|----|----|
| **师生交流时间极短** | 每周仅2小时课堂时间，全班10余个小组，每组实际获得的指导时间不足5分钟。 | 大部分实训过程处于无监督状态，问题积压至末期集中爆发。 |
| **开题答辩缺乏预演** | 开题时间短、老师质疑犀利，学生第一次接触压力答辩就是正式场合，无法提前修正方向。 | 每届有一定比例项目因开题准备不充分被要求换题，浪费前期投入。 |
| **进度评估仍然失真** | 老师/助教通常结合甘特图、阶段汇报和GitHub链接综合判断进度，但这些材料容易停留在“计划完成”或“界面已做出”的表层，难以反映后端实现、真实联调和工程质量。 | 代码质量问题往往积累到末期才被发现，纠错成本极高。 |
| **文档规范依赖学生自驱** | 各类文书（需求文档、设计文档、测试报告）规范性完全依赖模板和学生主动性，老师无暇逐一审查。 | 文档与代码实现严重脱节，工程素养培养目标落空。 |
| **成员贡献分配争议** | 实训末期组内打分缺乏客观数据支撑，工作量难以量化，部分成员对分数分配产生争议。 | 分配不公平影响团队协作积极性，也增加老师协调负担。 |

教育部 2025 年发布的《2024年全国教育事业发展统计公报》显示，2024
年全国共有各级各类学校 47万所，各种形式高等教育专任教师 216.35
万人；同一来源给出了普通本科学校 1257 所、本科层次职业学校 51
所、高职（专科）学校 1562 所、成人高校 249
所，说明高等教育数字化工具面向的是一个足够大的机构市场。[参考1](#ref-1)

同时，教育部 2025
年有关国家教育数字化战略行动的公开信息显示，国家教育数字化已进入 2.0
阶段，平台化、智能化、全过程赋能已是明确方向，国家智慧教育平台注册用户已突破
1.64
亿，表明高校教师和学生对数字化学习工具的接受基础已经形成。[参考2](#ref-2)[参考3](#ref-3)

### 2.2 这是一个“场景空白”，不是简单重复造轮子

现有产品大致分为两类：

1.  传统实训平台，如头歌、蓝桥、希冀，优势在于课程管理、实验环境、题目评测、班级组织。
2.  AI 编码工具，如 GitHub Copilot、Replit
    Agent，优势在于代码生成、开发提效、云端协作。

问题在于，两类产品都没有完整覆盖软件工程实训中的“教学治理”环节。它们要么偏管理，要么偏编码，却没有围绕“教学前置纠偏 +
工程过程监督 + 教师反馈提效 + 组内评价辅助”建立完整闭环。

例如，GitHub 官方页面明确表明，Copilot 的核心价值是提升开发生产率、在
IDE 和 GitHub 流程中提供代码建议、Agent、Code Review
等能力，而且对学生和教师可免费提供 Copilot Student/Pro
资格。[参考4](#ref-4)[参考5](#ref-5)
这意味着，单纯做“代码补全”没有进入价值，学生已经有低成本甚至零成本替代方案。

因此，本项目的立项逻辑不是再做一个 AI
编码助手，而做一个专门服务软件工程实训教学治理全流程的 AI
助教平台。这就是本项目值得投入的根本原因。

## 三、现有产品的旧体验与本产品的新体验

### 3.1 旧体验

| 场景 | 旧体验 | 造成的问题 |
|----|----|----|
| 项目开题 | 线下/PPT 快速答辩，时间短、问题少、修改滞后 | 项目可行性缺陷在正式开题后才暴露，换题成本高 |
| 开发过程 | 老师主要看阶段成果或 GitHub 链接，难以分析commit 细节 | 真实进度不透明，潜在 bug、安全问题、架构问题发现太晚 |
| 遇到问题 | 依赖老师、助教、同学临时答疑，课后反馈慢 | 学生卡点时间长，开发节奏中断 |
| 教师定时反馈 | 每组沟通时间短，且缺少会后沉淀 | 同类问题反复出现，沟通内容容易失真 |
| 组内评分 | 主要看主观印象、代码量或组员互评 | 容易引发公平争议，质量贡献难体现 |
| 使用 AI | 学生自己找通用 AI，对齐课程要求靠手工 | 文档和代码可能跑偏，容易依赖生成结果而非理解过程 |

### 3.2 新体验

| 场景 | 新体验 | 用户获得的核心价值 |
|----|----|----|
| 开题前 | AI 模拟答辩官按“市场需求、创新点、可行性、风险、实施计划”连续追问，并给出修改建议 | 在正式答辩前完成一轮低成本纠偏，减少无效选题 |
| 开发中 | 平台自动接入 GitHub 仓库，对每次 PR/commit 做规范、bug、安全、需求偏离检查 | 把问题发现时间从“周会后”提前到“提交后” |
| 难点求助 | 学生可向项目助教提问，平台结合课程 PPT、需求文档、仓库上下文给出启发式建议 | 减少纯通用 AI 的幻觉回答，提高课程贴合度 |
| 周反馈 | 系统自动生成项目健康周报、风险摘要、待跟进问题清单，分发给教师端、学生端 | 教师把有限时间用于关键决策，而非人工翻日志。学生更清楚自己项目目前缺点 |
| 期末评分 | 基于 commit 质量、PR 审查、文档贡献、问题修复、任务完成度生成组员评分建议 | 提供客观参考依据，降低评分争议 |

### 3.3 这项产品提供的新体验，本质上新在哪里

新不在于“把 AI 放进平台里”，而在于把 AI
放到软件工程实训中最稀缺、最难标准化的环节里：

1.  把答辩前移为可重复练习的模拟过程。
2.  把结果检查转为过程监督。
3.  把通用问答转为结合课程与仓库上下文的情境化辅导。
4.  把一次性主观评分转为全过程证据支持下的评分建议。
5.  把“直接给答案”改成“先启发再揭示”的防依赖机制。

## 四、产品方案与核心功能

### 4.1 目标用户

直接用户分为三类：

1.  教师/助教：需要节省检查时间、获得客观过程数据、提高反馈效率。
2.  学生/项目组：需要及时答疑、开题纠偏、开发问题预警和周度复盘。
3.  学院/课程负责人：需要教学留痕、过程数据、课程改进依据及工程教育认证支撑材料。

从系统形态上看，首版建议只做教师端和学生端两类核心端口，不额外拆分独立管理后台或家长端。教师端负责项目查看、风险汇总、周报与评分建议；学生端负责开题答辩、项目求助、问题接收与自查反馈。

### 4.2 核心功能模块

#### 模块一：开题模拟答辩

学生上传项目简介、需求描述、市场分析、技术选型、里程碑计划等后，AI
生成多轮追问。问题聚焦于：

1.  需求是否真实存在，用户是谁。
2.  创新点是否只是功能堆叠。
3.  技术方案是否过度承诺。
4.  团队能力与排期是否匹配。
5.  风险是否已识别并有备选方案。

输出包括：答辩问题记录、薄弱点诊断、建议修改清单、换题预警。

#### 模块二：GitHub 过程审查

平台接入 GitHub 仓库，自动分析
commit、PR、Issue、文档和分支活动，形成以下能力：

1.  代码规范性检查。
2.  潜在 bug 与安全风险提示。
3.  是否偏离需求文档或阶段目标的交付检查。
4.  提交节奏与任务分布分析。
5.  异常行为预警，如短时间大规模提交、长期零贡献、只做表面修改等。

#### 模块三：项目问题求助与课程对齐答疑

基于课程
PPT、实验要求、需求文档、项目仓库、往届优秀案例构建课程知识库，提供 RAG
驱动的项目助教。系统回答遵循“提示 -\> 思路 -\>
参考实现”的分层策略，避免直接代写。

#### 模块四：周报与教师辅助反馈

自动生成每组每周的：

1.  实际进度与计划偏差。
2.  本周高风险问题。
3.  未关闭缺陷与重复错误。
4.  文档与代码交付完成度。
5.  下周建议关注事项。

#### 模块五：组内贡献与评分建议

将贡献评价从“单纯代码行数”升级为“工作量 + 质量 +
责任承担”的综合建议，评价依据包括：

1.  commit 和 PR 数量与持续性。
2.  代码质量与缺陷修复贡献。
3.  文档撰写与更新情况。
4.  被合并采纳的设计方案或问题解决记录。
5.  对关键任务节点的承担情况。

平台只输出评分建议，最终评分权仍保留给小组与教师。

### 4.3 工程复杂性体现

本项目的难点不在于单次调用大模型，而在于把多个教学环节做成可持续运行的工程系统。其复杂性主要体现在：

1.  需要把 GitHub 的 commit、PR、Issue、文档更新、项目阶段目标等异构数据统一建模，而不是只做一次文本问答。
2.  开题答辩、代码审查、周报生成、评分建议的输入输出结构不同，需要设计稳定的任务编排流程；后续可以演进为多智能体协同，但首版更适合采用“规则 + 工作流 + 大模型”的方式实现。
3.  课程材料 RAG 不是简单上传文档，还涉及资料切分、向量检索、课程上下文对齐、答案可追溯等工程问题。
4.  平台需要同时满足“能辅助教学”与“不能明显诱导代写”两种相反约束，因此回答策略、证据展示和权限边界都需要额外设计。

## 五、原创性与差异化：为什么它比现有产品更值得做

### 5.1 项目的原创性判断

本项目不是基础模型创新，也不是做新的编程语言工具链，因此不以算法原创性作为立项前提。它的原创性体现在场景组合创新和教学机制创新上：

1.  把开题答辩、项目管理、GitHub
    过程审查、课程对齐答疑、组内评分建议整合进一个软件工程实训闭环。
2.  让 AI 面向“教学治理”而不是仅面向“写代码”。
3.  把课程 PPT、项目需求、仓库上下文、组内协作数据融合为同一助教上下文。

换言之，这是一个面向高校实训组织方式重构的产品。

### 5.2 与现有竞品相比，好在哪里

| 对比对象 | 现有优势 | 现有短板 | 我们的优势 |
|----|----|----|----|
| 头歌/蓝桥/希冀等实训平台 | 实验环境、课程组织、题目评测成熟 | 更偏课程管理和实验交付，缺少对真实 GitHub 项目过程的教学治理 | 强调项目全过程、GitHub 接入、开题纠偏和评分辅助 |
| GitHub Copilot / Replit | 编码提效强、反馈快 | 默认导向是“更快完成”，不以教学理解和课程对齐为优先 | 以启发式辅导、防代写、课程知识库和阶段目标对齐为核心 |
| 通用大模型问答工具 | 成本低、入口方便 | 无法感知课程边界、教师要求和项目上下文，容易幻觉 | 基于课程资料和项目仓库的情境化回答，更适合教学场景 |

### 5.3 为什么我们有机会做出别人没做好的点

因为我们切入的不是通用开发工具市场，而是院校教学流程中的低效率空白。这个空白具备三个特点：

1.  场景高度细分，大厂不一定优先解决。
2.  教学流程需要强本地化、强课程化配置，通用工具很难直接适配。
3.  教师真正需要的是“节省判断成本”和“保留教学主导权”，而不是单纯多一个
    AI 聊天入口。

## 六、用户价值：平台与用户的交易到底是什么

### 6.1 对学生的用户价值

学生换回来的价值是：

1.  在正式开题前获得一次高强度预演，减少低级失误。
2.  在开发过程中获得更早的问题发现与更快的卡点解决。
3.  获得贴合课程要求的建议，而不是泛泛的 AI 答案。
4.  在期末评价中有更清晰的个人贡献证据。

### 6.2 对教师的用户价值

教师将部分重复性检查工作交给系统。教师换回来的价值是：

1.  更快识别高风险组和高风险问题。
2.  将有限指导时间投向真正需要判断的环节。
3.  获得周报、记录和过程证据，减少凭印象管理。
4.  在成绩评定、课程复盘和认证材料整理时降低事务成本。

### 6.3 对学院与学校的用户价值

1.  提高实训课程质量可见度。
2.  形成过程数据资产，支撑课程改进和专业建设。
3.  为工程教育认证、竞赛组织、校企实践项目提供可追溯证据。
4.  展示 AI 赋能教学改革成果，具备宣传和示范价值。

## 七、如何降低替换成本

高校采购和落地教育产品，最大的障碍通常不是功能不足，而是替换成本太高。若本项目想真正落地，必须刻意降低替换成本。

### 7.1 教学替换成本最小化

1.  教师不需要重写课程体系，只需上传已有课件、任务书、评分标准。
2.  评分建议仅作参考，不强制替代教师评分。
3.  开题模拟、过程审查、周报等功能可按需订阅。
4.  平台优先服务老师现有流程，而不是强行改变老师的授课方式。

## 八、市场分析：需求是否真实，市场规模是否足够

### 8.1 市场需求为什么是真需求

本项目不依赖“学生喜欢用
AI”这一表面现象立项，而是建立在三个更稳定的需求之上：

1.  高校软件工程实训本身是长期存在的必修教学活动。
2.  教师时间稀缺与过程评价困难，是随着项目制教学普及而持续存在的问题。
3.  GitHub、Copilot 等工具普及后，老师更需要“教学管理侧
    AI”，而不是“再多一个生成工具”。

因此，本项目不是追热点，而是顺着教学组织的真实痛点切入。

### 8.2 市场空间测算

从机构侧看，2024 年我国普通本科学校 1257 所、本科层次职业学校 51
所、高职（专科）学校 1562 所，合计面向高等教育的潜在机构数量已超过 2800
所；若纳入成人高校，总量更高。[参考1](#ref-1)

本项目初期不面向全部高校，而聚焦开设软件工程、计算机科学与技术、人工智能、数据科学、数字媒体技术等项目制课程较多的院校。若保守假设仅有
30% 的相关院校具备首批采用可能，按 800
所学校计算（以下仅统计项目订阅费，不计API费用）：

1.  若基础版按每校每年 6 万元订阅，则对应约 4800 万元年化市场。
2.  若专业版按每校每年 10 万至 15 万元订阅，则对应约 8000 万至 1.2
    亿元年化市场。
3.  若再叠加私有化部署、课程知识库建设、认证材料支持、校企联合实践等项目型收入，市场上限还会继续扩大。

以上为基于公开院校数量进行的自下而上估算，不是行业报告口径，但对于立项阶段判断“是否有足够机构客户可切入”已经足够。

### 8.3 市场空白在哪里

市场空白主要体现在三个层面：

1.  有课程平台，但缺少专门面向 GitHub 项目过程的教学评价工具。
2.  有通用 AI 编码工具，但缺少AI教学全过程引导的产品。
3.  有结果评分系统，但缺少面向组内贡献、公平建议和阶段性风险预警的过程工具。

## 九、盈利模式：这个项目为什么“有利可图”

### 9.1 核心收入来源

1.  院校 SaaS 订阅费：按课程数、班级数、活跃项目组数或教师数收费。
2.  私有化部署费：面向重视数据安全、校内算力或本地知识库的学院和学校。
3.  增值模块费：如 GitHub
    深度审查、课程知识库建设、工程教育认证报表、竞赛模式、校企项目模式。
4.  实施与培训服务费：教师培训、课程上线辅导、历史资料整理与导入。

### 9.2 为什么具备盈利可行性

1.  客户是机构，不是单个学生，客单价高于个人工具。
2.  平台嵌入教学流程后，续费概率高，收入具备年周期稳定性。
3.  数据和知识库积累越多，平台切换成本越高，客户粘性会增强。
4.  高校通常允许先试点、后全院推广，便于从小单验证走向大单扩张。

### 9.3 为什么不会陷入纯模型成本内卷

如果产品只是“问答 + 代码生成”，很容易陷入模型能力同质化和 token
成本竞争。但本项目的价值重点在于：

1.  教学流程嵌入。
2.  课程知识库与评分规则沉淀。
3.  GitHub 过程数据分析能力。
4.  教师管理看板与认证材料输出。

这些部分决定了产品不只是大模型转售，而是有明确业务壁垒的软件系统。

## 十、MVP 验证方案

### 10.1 MVP 范围

首版不追求大而全，只验证最核心闭环：

1.  开题模拟答辩。
2.  GitHub 仓库接入与 commit/PR 风险审查。
3.  每周项目健康摘要。
4.  基础的组员贡献可视化。

### 10.2 试点对象

当前阶段不宜一开始覆盖整门课程或整个班级，建议先以 3 至 5
个项目组的小规模试点验证核心流程。这个规模更适合 12
周开发周期下的 MVP 验证，也便于快速收集可执行反馈。

### 10.3 MVP 成功指标

当前阶段的 MVP 指标应以“功能可用性”和“小范围试用反馈”为主，而不是直接承诺大规模教学效果。建议采用以下验证指标：

1.  至少完成 3 个项目组的真实仓库接入，并成功拉取 commit、PR 和基础项目信息。
2.  每个试点项目组至少完成 1 轮开题模拟答辩，并生成结构化问题清单与修改建议。
3.  系统能够对真实提交记录生成至少 1 份周报和 1 份问题摘要，且教师能读懂并指出其是否有参考价值。
4.  至少邀请 3 至 5 名试用者完成访谈或问卷，确认他们是否认可“开题模拟”和“过程审查”两个核心功能的使用价值。
5.  在试点结束后，能够明确识别出哪些功能值得保留到下一版，哪些功能应延后开发。

### 10.4 为什么必须先做 MVP

因为高校教学产品的风险不在于“做不出来”，而在于“做了但老师不用”。MVP
的价值在于尽快验证三件事：

1.  教师和学生是否愿意实际接入项目仓库并持续使用。
2.  开题模拟答辩和过程审查是否真的比单纯聊天问答更有价值。
3.  在小规模试点下，哪些功能能稳定跑通，哪些功能暂时只适合作为后续规划。

## 十一、风险与应对

### 11.1 风险一：学生把平台当代写工具

应对策略：

1.  默认启用分层回答机制，优先提示与追问。
2.  对高风险场景限制直接生成完整答案。
3.  结合代码演进记录判断是否存在突增式外部粘贴。

### 11.2 风险二：教师不信任 AI 评分

应对策略：

1.  所有评分建议必须可追溯到证据。
2.  平台只提供建议，不直接替代教师打分。
3.  在产品前期优先输出“依据”和“异常提示”，而不是直接给分。

### 11.3 风险三：数据安全与代码隐私顾虑

应对策略：

1.  提供公有云版与私有化版两种部署路径。
2.  对仓库访问权限、日志保留、模型调用范围做细粒度控制。
3.  敏感项目支持校内部署和本地知识库。

### 11.4 风险四：产品范围过大，研发失控

应对策略：

1.  严格按 MVP 先验证关键闭环。
2.  首期只保留教师端和学生端，不扩展更多角色端口。
3.  首轮验证规模控制在 3 至 5 个项目组，不追求全班覆盖。
4.  首期只围绕 GitHub 流程和课程资料接入，不自建复杂 IDE，也不强行一次性做完整多智能体体系。

## 十二、最终立项结论

综合需求真实性、竞品空白、替换成本、可盈利性和实施可行性，本项目具备立项价值。

立项的关键不是把它做成大而全的教学平台，而是坚定聚焦于一个清晰定位：面向高校软件工程实训全过程的
AI
助教平台。它解决的不是“学生不会写代码”这么简单的问题，而是教师无法高密度陪跑每一个项目组，而项目制教学又高度依赖过程反馈这一更关键的组织问题。

从商业上看，它有机构付费空间；从产品上看，它有明确场景边界；从落地上看，它可以外挂式接入现有流程；从创新上看，它并非重复造一个通用
AI，而是在高校软件工程实训这一细分场景中重构旧体验。

因此，小组应该投入资源立项，并以小范围试点、数据验证、分阶段扩展的方式推进。
